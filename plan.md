# PLAN: GatorGraph (Visual, AI-Assisted Degree Planner for SFSU)

This file is the single source of truth. An LLM coding agent should be able to build the whole project from this file alone. Read all of it before writing code. Follow the "Rules for the coding agent" in section 17.

---

## 1. One-line pitch

GatorGraph turns the text-heavy SFSU degree audit into an interactive map. Courses are nodes. Semesters are dotted boxes. Prerequisites are red lines. A rules engine checks the plan. Gemini builds plans from career goals and explains the plan in plain words.

Hackathon: SF Hacks x GDG AI Hackathon at SFSU.
Tracks: SFSU track (real student and administration problem) and GDG track (meaningful use of Gemini).

---

## 2. Non-negotiables (from the builder)

1. NOT an AI wrapper. The core value is a deterministic rules engine and a visual map. Gemini is used for planning and explaining, never as the source of truth for rules.
2. NOT a log or tracker tool.
3. No integration with SFSU systems. No login to SFSU. Demo must run live from public data only.
4. Every course, prerequisite, credit value and policy must come from a validated public source with a link. No guesses. If data is unknown, mark it unknown and show it as unknown in the UI.
5. Demoable live on a laptop in under 3 minutes.
6. Visual quality matters as much as function.

---

## 3. Problem statement (must be backed with sources before the pitch)

Claim to prove with evidence:
- The current SFSU degree audit page is a long table with status icons (done, in progress, not done). It is hard to scan.
- The degree planner shows next-semester courses but does not show how courses connect, and does not connect courses to career goals.
- Prerequisite chains are hard to see in the Bulletin because they are written as text.

Evidence tasks (do these in the first 20 minutes, store in `docs/evidence.md`):
- [ ] Take screenshots of the current degree audit and planner pages (student's own view, blur personal data).
- [ ] Collect the SFSU Bulletin URLs for the CS major, course descriptions, and the unit/credit policies. Paste real URLs only. Do not invent links.
- [ ] Find 1 or 2 published sources about advising load or time-to-degree at SFSU or in the CSU system. Link them. If none can be found fast, drop the statistic and say "student-reported" instead.
- [ ] Ask the SFSU teammate for 2 real quotes about the pain. Mark them as anecdotal.

Who benefits:
- Students: see the whole path, catch prerequisite mistakes before registration, connect courses to careers.
- Advisors and administration: fewer avoidable advising appointments about prerequisite order and unit load. Frame as a hypothesis, not a measured result.

## 5. Tech stack (decisions with reasons)

### Frontend
- Vite + React + TypeScript.
- **React Flow (package `@xyflow/react`)** for the map.
  - Why: it supports custom nodes, group/parent nodes (semester boxes), edges that follow nodes when dragged, zoom and pan, and a drag-from-sidebar pattern. LeaderLine.js (old plan) draws lines over the DOM and breaks on scroll, zoom and drag. React Flow does not.
  - Semester box = a custom group node with a dashed border. Course = child node with `parentId` set to the semester node.
- Tailwind CSS for styling.
- Zustand for state (simple, no boilerplate).
- Framer Motion (optional) for panel slide and node animations.
- No dagre or auto layout library needed. Layout is a fixed column grid computed by code.

Alternatives considered:
- Cytoscape.js: strong for chaotic graphs, weak for strict columns and drag into containers.
- D3: too much manual work for the time limit.
- Graphify: not needed. React Flow gives the same "map" look with more control.
- Keep LeaderLine plan: lower risk only if the team refuses React. It is fine to fall back to it, but expect line repositioning bugs.

### Backend
- Python 3 + Flask. Only two jobs: serve built frontend, and proxy Gemini calls so the API key never reaches the browser.
- The rules engine lives in TypeScript in `shared/` and is used on the client. The server re-runs the same checks on AI output. To avoid writing the engine twice, choose ONE:
  - Option A (recommended): write the engine in TypeScript, and have the Flask server call a small Node script, or move the AI proxy to a Node/Express server. This keeps one engine.
  - Option B: write the engine in Python and also in TS (two copies). Only if Option A is blocked.
  - Decide in the first 15 minutes. Default to Option A with an Express server instead of Flask. If the team is more comfortable with Flask, use Option B and write a shared JSON test file that both engines must pass.

### AI
- Google GenAI SDK (`google-genai` for Python or `@google/genai` for Node).
- Model ID must come from an environment variable `GEMINI_MODEL`. Check the current model names in the official Gemini docs on the day. Do not hardcode from memory. Use a fast model for evaluate, and a stronger model for plan if latency allows.
- Use structured output: `response_mime_type = "application/json"` with a `response_schema`. Never parse free text.

### Hosting for demo
- Run locally for the live demo. Deploy to Render, Vercel or similar only as a backup link. Have a screen recording as a second backup.

## 7. Data model

All IDs are normalized without spaces: `CSC413`, not `CSC 413`.

### 7.1 Course (`data/catalog.json`)

```json
{
  "id": "CSC413",
  "dept": "CSC",
  "number": "413",
  "name": "Software Development",
  "units": 3,
  "oneLiner": "Team-based software engineering practice.",
  "description": "Full catalog description text, copied from the source.",
  "prereqs": [["CSC340"], ["CSC230", "CSC231"]],
  "coreqs": [],
  "tags": ["core", "software-eng"],
  "typicalTerms": ["fall", "spring"],
  "sourceUrl": "https://...",
  "sourceAccessed": "2026-10-02",
  "verified": true,
  "notes": ""
}
```

Rules:
- `prereqs` is AND of OR groups. Outer array = AND. Inner array = OR. Example above means: CSC340 AND (CSC230 OR CSC231).
- `units` is the credit value. Use the word "credits" in the UI.
- `oneLiner` is a short summary under 90 characters. If written by hand or by Gemini, set `oneLinerSource: "generated"`. The full `description` stays as the official text.
- `typicalTerms` is only filled if the source says so. Otherwise `[]` and the engine does not check term offering.
- `verified: false` courses show a small "unverified" badge in the UI. Do not hide them.
- Prerequisites written in prose that cannot be parsed cleanly (for example "or consent of instructor", "or equivalent", "or placement exam") go into `prereqNotes` (string). The engine ignores `prereqNotes` for errors and shows them as info.

### 7.2 Program (`data/programs/bs-computer-science.json`)

```json
{
  "id": "bs-cs",
  "name": "B.S. Computer Science",
  "totalUnitsRequired": 120,
  "sourceUrl": "https://...",
  "requirementGroups": [
    {
      "id": "lower-core",
      "title": "Lower Division Core",
      "type": "all",
      "courseIds": ["CSC210", "CSC220"]
    },
    {
      "id": "upper-electives",
      "title": "Upper Division Electives",
      "type": "pickN",
      "n": 4,
      "courseIds": ["CSC450", "CSC470"]
    },
    {
      "id": "ge",
      "title": "General Education",
      "type": "units",
      "unitsRequired": 48,
      "note": "Modeled as placeholder blocks, see 7.4"
    }
  ]
}
```

Group types: `all` (every course needed), `pickN` (choose N courses), `units` (needs X units, used for GE or free electives).

### 7.3 Policies (`data/policies.json`)

Each policy has a value and a source. These are configuration, not hardcoded constants in code.

```json
{
  "minUnitsFullTime": { "value": 12, "sourceUrl": "https://...", "verified": false },
  "heavyLoadUnits": { "value": 18, "sourceUrl": "https://...", "verified": false },
  "maxUnitsWithoutPermission": { "value": 18, "sourceUrl": "https://...", "verified": false }
}
```

The 12 and 18 numbers are from the first draft of this plan. They MUST be checked against the Bulletin or registrar page before the demo. Until verified, the UI shows the rule as "assumed" in the evaluate panel.

### 7.4 General Education handling

GE is large and messy. For P0, model GE as generic placeholder cards: "GE Area A (3u)", "GE Area B (3u)" and so on, tagged `ge`, with no prerequisites. This lets the semester credit totals look realistic without scraping the GE catalog. Mark them clearly as placeholders. Do not pretend they are specific courses.

### 7.5 Plan and board state

```json
{
  "id": "plan_1",
  "name": "Quant path",
  "programId": "bs-cs",
  "goalText": "Quant developer at a trading firm",
  "createdAt": "2026-10-02T10:00:00Z",
  "semesters": [
    { "index": 1, "label": "Fall Year 1", "courseIds": ["CSC210", "MATH226"] },
    { "index": 2, "label": "Spring Year 1", "courseIds": [] }
  ],
  "lastEvaluation": null
}
```

- Exactly 8 semesters in P0. Labels: Fall/Spring Year 1 to 4.
- A course ID appears in at most one semester per plan.
- "Unassigned" = all program-relevant catalog courses not in any semester. This list feeds the left panel.
- All plans are stored in `localStorage` under key `gatorgraph.plans.v1`. Include a `Reset` button.

### 7.6 Career directions (`data/career_tags.json`)

```json
{
  "directions": [
    {
      "id": "quant",
      "label": "Quantitative Developer / Quant",
      "signalTags": ["math", "algorithms", "probability", "numerical"],
      "signalCourseIds": ["CSC220", "MATH324"],
      "description": "Math-heavy, performance-focused software roles."
    }
  ]
}
```

Build 6 to 8 directions: Software Engineer, Quant, Data/ML Engineer, Cybersecurity, Systems/Networking, Product/Business-tech (needs P1 Business data), Game/Graphics, Academia/Research. Signals only use courses that exist in the verified catalog.

## 8. Data pipeline (scraping, with validation)

Goal: reproducible and checkable. Not clever.

Steps:
1. `data/sources.md`: list every URL, what it is used for, date accessed.
2. `scripts/scrape_bulletin.py`:
   - Use `requests` and `BeautifulSoup`.
   - Respect robots.txt and rate limit (1 request per second). Cache raw HTML in `data/raw/`.
   - Input: the program page URL. Output: list of course IDs, then each course page parsed into the course schema.
   - Parse prerequisites with simple regex into the AND/OR structure. Anything the regex cannot parse cleanly goes into `prereqNotes` and flags the course for manual review.
3. `scripts/validate_catalog.py` checks:
   - Every course has id, name, units, sourceUrl.
   - Every prerequisite ID exists in the catalog (if not, add a stub course with `verified:false` or fix it).
   - No prerequisite cycles.
   - No duplicate IDs.
   - Prints a list of courses flagged for manual review.
4. Manual review: the SFSU teammate checks the flagged courses and a random sample of 10 more against the live Bulletin. Mark `verified: true` only after a human check.
5. Time box: 75 minutes total for the data. If the scraper is not working at 30 minutes, type the data by hand from the Bulletin into JSON. Hand-typed and verified beats scraped and wrong.

Do NOT use the Gemini API to invent prerequisites or course facts. Gemini may be used to draft `oneLiner` text from the real description, and those are flagged `generated`.

## 9. Rules engine (`shared/engine.ts`)

Pure functions. No network. Fully unit tested. This is the credibility of the project.

### 9.1 Input and output

```ts
evaluatePlan(plan, catalog, program, policies): EngineReport
```

```ts
type Issue = {
  id: string
  severity: "error" | "warning" | "info"
  code: string               // see list below
  message: string            // plain English, short
  courseIds: string[]
  semesterIndex?: number
  sourceUrl?: string         // for policy-based issues
}

type EngineReport = {
  issues: Issue[]
  semesterStats: { index: number; units: number; status: "empty" | "under" | "ok" | "heavy" | "over" }[]
  requirementStatus: {
    groupId: string
    title: string
    satisfied: boolean
    missingCourseIds: string[]
    unitsHave?: number
    unitsNeed?: number
  }[]
  totalUnitsPlanned: number
  graduationReady: boolean   // true only if no errors and all requirement groups satisfied and total units met
}
```

### 9.2 Rules

| Code | Severity | Rule |
|---|---|---|
| `PREREQ_ORDER` | error | A course is in semester S. For each AND group in its prereqs, at least one OR option must be in a semester strictly before S. Otherwise error. |
| `PREREQ_MISSING` | error | The prerequisite course is not anywhere in the plan. Message names the missing options. |
| `COREQ_ORDER` | error | A corequisite must be in the same semester or earlier. |
| `UNITS_UNDER` | warning | Semester units below `minUnitsFullTime` and semester is not empty. |
| `UNITS_HEAVY` | warning | Units above `heavyLoadUnits`. |
| `UNITS_OVER` | error | Units above `maxUnitsWithoutPermission`. |
| `DUPLICATE_COURSE` | error | Same course twice in a plan. (Should be blocked by UI, kept as a safety check.) |
| `REQ_GROUP_INCOMPLETE` | warning | A requirement group is not satisfied by the plan. Lists missing courses. |
| `TOTAL_UNITS_SHORT` | warning | Planned units below `totalUnitsRequired`. |
| `TERM_NOT_OFFERED` | info | Only if `typicalTerms` is filled and the semester season is not in it. Soft, because offerings change. |
| `UNVERIFIED_DATA` | info | Plan uses courses with `verified:false`. |
| `PREREQ_NOTE` | info | Course has `prereqNotes` the engine cannot check. |

Semester status for the box color:
- `empty`: no courses.
- `under`: units < min and not empty.
- `ok`: min <= units <= heavy.
- `heavy`: heavy < units <= max.
- `over`: units > max.

### 9.3 Tests (write these first)
- Prereq in earlier semester passes. Same semester fails. Later semester fails. Absent fails.
- OR group: either option passes.
- AND group: both groups needed.
- Credit boundaries at exactly 12, 18, 19.
- pickN group with fewer than N chosen.
- A fully valid sample plan returns `graduationReady: true` (build this fixture by hand from the real program).

### 10.2 Semester node (the dotted square)
- Custom group node. Width 260px. Height grows with course count (min height 220px).
- Header: label ("Fall Year 1"), unit total ("14 units"), small status chip.
- Border: 2px dashed.
  - `empty`: gray dashed, light background.
  - `ok`: green-tinted dashed.
  - `under`: red dashed, red-tinted background, chip "Below 12".
  - `heavy`: amber dashed, chip "Heavy".
  - `over`: red solid dashed and strong tint, chip "Over limit".
- Year grouping: a thin label above each pair of semesters ("Year 1"). 8 boxes in a single horizontal row so prerequisite lines flow left to right.
- Dropping a course on a semester sets `parentId` and snaps it to the next free slot in the stack.
- Empty semester is NOT red. Red only appears when it has at least one course and is under the minimum. (Reason: a fully red board while building is noise.)

### 10.3 Course node
- Compact card (width 220px). Shows: course ID (bold), short name, credits badge.
- Left color stripe by category: core, elective, GE placeholder, math, other.
- Hover card (appears after 150 ms delay, positioned beside the node):
  - Course ID and full name
  - One-liner
  - Credits
  - Prerequisites in readable form ("CSC340 and (CSC230 or CSC231)")
  - Source link ("View in Bulletin")
  - "Unverified" badge if `verified:false`
- Click selects the node and highlights its full prerequisite chain (upstream) and dependents (downstream). All other nodes and edges dim to 25 percent opacity. Click on empty canvas clears the highlight. This is the best "wow" interaction. Build it.
- Course nodes can be dragged out of a semester back to the sidebar to unassign. Also provide an "x" button on hover.
- Courses with an error show a small red dot badge.

### 10.4 Edges
- One edge per (prerequisite course, dependent course) pair where both are on the board.
- Type: smooth step or bezier, from the right handle of the prerequisite to the left handle of the dependent.
- States:
  - Satisfied (prereq in an earlier semester): red, 1.5px, with arrow head. (Red is the builder's requirement. Keep the thickness low so many lines stay readable.)
  - Violated (same semester, later semester): red, 3px, animated dashes, with a warning icon on the midpoint.
  - OR-group alternatives: dashed line style. Label "or" at midpoint.
  - Corequisite: blue dotted.
- Missing prerequisite (not on board): no edge. The dependent node shows a small "needs CSC340" ghost chip. Clicking the chip adds the missing course to the first valid earlier semester if possible, otherwise to the sidebar highlight.
- Legend must explain every line style and every semester border style.

### 10.5 Sidebar
- Title "Courses". Search input (matches ID and name).
- Filter chips: All, Required, Electives, Math, GE, Verified only.
- Courses grouped by requirement group (from the program file). Each group shows progress ("3 of 4 chosen").
- Each item is draggable. Dragging uses the React Flow sidebar drag pattern: `onDragStart` sets `dataTransfer` with the course ID, canvas `onDrop` converts screen position to flow position and finds the semester under the pointer.
- If the drop is not over a semester, ignore the drop and flash the sidebar item.
- Items already placed in the plan are hidden from the list (or grayed with a "placed in Sem N" tag).

### 10.6 Toolbar and multiple plans
- Tabs for plans. Double click to rename. "+ New plan" creates an empty plan. "Duplicate" copies the current plan (useful for "what if" tests).
- Active plan id stored in the Zustand store and localStorage.
- P1: "Compare" opens two plans side by side with differences highlighted (courses present in only one plan).

### 10.7 AI Plan modal
- Opens on "AI Plan".
- Text: "What do you want to do in life?"
- Large textarea plus 6 quick-pick chips from `career_tags.json` (Quant, Cybersecurity, ML, Software Engineer, Systems, Game dev).
- Optional controls: "Units per semester target" (default 15), "Keep my current courses" toggle (if on, the AI only fills the rest).
- Submit shows a progress state ("Reading requirements", "Building semesters", "Checking prerequisites"). These messages are real stages: call, validate, repair, display.
- On success, create a NEW plan tab (do not overwrite the current plan) named from the goal. Animate courses flying into semesters one by one (nice to have).
- On failure after retries, show a clear error and offer the deterministic fallback plan (see 11.2).

### 10.8 Evaluate panel
- Opens from the right on "Evaluate".
- Sections in this order:
  1. Verdict banner: "Valid plan", "Fix 2 errors first", or "Valid but incomplete".
  2. Errors (engine). Each item is clickable and focuses the related courses on the canvas.
  3. Warnings (engine).
  4. Missing requirements (engine, grouped by requirement group).
  5. Career direction (engine scores plus Gemini explanation): a small horizontal bar chart of direction scores, with the top direction named and 2 or 3 sentences of explanation.
  6. Suggestions (Gemini): up to 3 concrete swaps, each referencing real course IDs. The engine validates each suggestion and the UI only shows suggestions that do not create new errors.
  7. Info items (unverified data, notes).
- Every engine item can show its `sourceUrl` link when it comes from a policy.
- The panel shows a "Generated by Gemini" label on AI sections and "Checked by rules engine" on engine sections. This is part of the honesty story.

### 10.9 Visual design
- Dark navy canvas with a subtle dot grid is fine, but SFSU colors (purple #231161 and gold #E3B53C, verify on the SFSU brand page) should appear in the header and accents.
- Fonts: Inter for UI. Monospace for course IDs.
- Smooth transitions on semester color change (200 ms).
- Mobile is out of scope. Optimize for a 1440 x 900 laptop and a projector.

## 11. AI design

Principle: Gemini proposes, the engine decides.

### 11.1 AI Plan flow (`POST /api/plan`)

Request:
```json
{
  "goalText": "Quant developer",
  "programId": "bs-cs",
  "unitsPerSemester": 15,
  "lockedPlacements": [{ "courseId": "CSC210", "semester": 1 }]
}
```

Server steps:
1. Load catalog, program, policies. Build a compact course list for the prompt: `id | name | units | prereqs | tags | oneLiner`. Only include courses relevant to the program (keep the prompt small and fast).
2. Call Gemini with structured output.
3. Parse JSON. Validate with the engine.
4. If there are errors, do ONE repair call: send the engine errors back to Gemini and ask for a corrected plan. Maximum 2 repair attempts.
5. If still invalid, run the deterministic fallback (11.2) and set `source: "fallback"` in the response.
6. Return the plan, the engine report, and Gemini's short rationale.

System prompt (store in `server/prompts`):
```
You are a degree planning assistant for San Francisco State University.
You will receive a list of courses with their prerequisites, a student's career goal, and rules.
Build an 8 semester plan for the B.S. Computer Science program.

Hard rules:
1. Use ONLY course IDs from the provided list. Never invent a course.
2. A course may appear only once.
3. Every prerequisite must be placed in an EARLIER semester than the course that needs it.
4. Each semester must have between {min} and {max} units. Aim for {target}.
5. Every required course in the requirement groups must appear exactly once.
6. For "pick N" groups, choose the N courses that best fit the student's goal.
7. Use GE placeholder courses to fill units where needed.

Goal handling:
- Prefer electives whose tags match the goal.
- Put foundations early and specialized electives in later semesters.

Return ONLY JSON that matches the schema. No extra text.
```

Response schema:
```json
{
  "semesters": [{ "index": 1, "courseIds": ["..."] }],
  "rationale": "2 to 4 plain sentences on why these electives fit the goal",
  "electiveChoices": [{ "courseId": "...", "reason": "one sentence" }]
}
```

### 11.2 Deterministic fallback planner
Written in code, no AI. Topological sort of required courses by prerequisite depth, then fill semesters up to the target units, then add goal-matching electives using tag scores. This guarantees the live demo never shows an empty result. It is also a talking point: "AI is optional for validity."

### 11.3 Evaluate flow (`POST /api/evaluate`)

Order matters:
1. Run the engine on the plan. This is the truth.
2. Compute career direction scores in code: for each direction, score = weighted count of planned courses matching its `signalTags` and `signalCourseIds`, normalized to 0 to 100.
3. Send ONLY a summary to Gemini: the plan, the engine issues, the missing requirements, the top 3 direction scores, and the optional goal text. Ask Gemini to explain in plain language and suggest up to 3 swaps.
4. Validate every suggested swap with the engine. Drop any suggestion that introduces an error or uses an unknown course ID.
5. Return `{ engineReport, directionScores, aiExplanation, suggestions }`.

System prompt:
```
You are an academic advisor assistant.
You receive a student's plan, a list of rule violations already found by a rules engine,
and career direction scores computed by code.

Do not recompute or contradict the rules engine. Treat it as correct.
Do not invent courses. Use only course IDs from the plan or the provided course list.

Write:
1. "summary": 2 to 3 plain sentences on the overall state of the plan.
2. "directionExplanation": 2 to 3 sentences on which career direction this plan points to and why, using the provided scores.
3. "suggestions": up to 3 swaps. Each has "remove" (course id or null), "add" (course id), "semester" (index), and "reason" (one sentence).

Use simple words. Be direct. If the plan is fine, say so.
Return ONLY JSON.
```

### 11.4 AI safety and honesty rules
- Never show AI text that names a course not in the catalog.
- Never let AI change policy values.
- Label every AI-generated block in the UI.
- Add a footer in the Evaluate panel: "Always confirm with your SFSU advisor." This protects students and helps the pitch to administration.

### 11.5 Latency and cost
- Cache AI plan responses by hash of (goalText, program, units target) in server memory for the demo. Pre-warm the 3 demo goals before presenting.
- Set a 25 second timeout per Gemini call with one retry.

## 13. Layout algorithm (`web/src/lib/layout.ts`)

- Semester box i has x = 40 + (i - 1) * (260 + 40), y = 80.
- Course nodes inside a semester use relative positions: x = 20, y = 60 + k * 76 where k is the index in that semester's course list.
- Semester height = max(220, 60 + count * 76 + 30).
- After any move, recompute positions for the affected semesters and set node `parentId`.
- Use `extent: "parent"` so courses cannot leave their semester by dragging. Unassigning happens through the sidebar drop zone or the "x" button.
- Edges are derived from state on every render. Never store edges as source of truth.

State is the plan JSON (section 7.5). Nodes and edges are always derived from it. This keeps multiple plans and undo simple.

## 19. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Scraper fails or parses prerequisites wrongly | High | Hand-type data. Validator script. Human review of flagged and sampled courses. |
| Wrong policy numbers (12 and 18 units) | High | Verify on official pages. Show `assumed` label until verified. |
| React Flow group node and drag edge cases eat time | Medium | Use the official sidebar drag example. Fixed layout. `extent: parent`. |
| Gemini returns invalid JSON or invalid plan | Medium | Structured output, repair loop, deterministic fallback. |
| Gemini latency or quota in the demo | Medium | Cache and pre-warm, backup video, hotspot. |
| Too many red lines look like spaghetti | Medium | Thin satisfied edges, click-to-highlight, dim others. |
| Scope creep to "all majors" | High | Strict P0. All majors is roadmap only. |
| Prerequisites that are prose only (consent of instructor) | Low | `prereqNotes` as info, not error. |
| Claims in the pitch without evidence | Medium | Evidence file. Label hypotheses as hypotheses. |
